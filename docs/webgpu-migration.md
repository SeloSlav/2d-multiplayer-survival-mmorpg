# WebGPU world presentation migration

The target is a real 3D world rendered exclusively by Three.js WebGPU, with a fixed low oblique orthographic camera 30° above the ground so the survivor's face remains visible, and a deliberately low-resolution image. UI and inventory icons remain 2D. SpacetimeDB, authoritative coordinates, collision, prediction, reducers, and gameplay rules remain authoritative.

## Visual contract

- **UI is locked.** The user requires the existing game UI to remain byte-for-byte unchanged. Do not edit existing React UI components, styles, fonts, icons, menus, HUD, inventory, or UI painter implementations. `npm run verify:ui-unchanged` verifies 719 existing source/assets against Git and a local raw-byte lock, including the checkout's original line endings. Keep the game entry and `GameCanvas.tsx` unchanged. The engine creates a separate WebGPU canvas underneath the original full-resolution UI/input canvas and reuses the original UI painters. Inspection UI exists only in the standalone development page.
- Art direction: finer pixelated low-poly models, as explicitly chosen by the user; refine the initial silhouettes toward this direction.

- One presentation unit is one 48 px gameplay tile. The X/Z ground transform compensates the fixed camera tilt so the existing screen-to-world input remains exact on the ground.
- Model silhouettes, layered materials, articulated movement, hand sockets, directional shadows, and local firelight must read before post effects. World sprites, camera-facing sprite characters, and billboard vegetation do not count as migrated.
- Deterministic asset variants derive from entity IDs. The engine lab uses seed 73021 and the same renderer and model factories as gameplay.
- Initial image resolution is half CSS resolution, enlarged with nearest-neighbor filtering. Camera orientation is fixed; resizing changes the orthographic bounds.
- WebGPU initialization must fail visibly when unavailable. No Canvas2D or WebGL fallback may render the world.
- Target: 60 Hz presentation at a 1280×720 CSS viewport. CPU timings and draw counts are diagnostics, not a claim of measured GPU time.

## Completion gates

1. Engine foundation: WebGPU-only lifecycle, deterministic inspection scene, exact camera/input mapping, resize and teardown, explicit unsupported-device UI.
2. Player: recognizable model, all equipment meshes and attachment sockets, idle/walk/sprint/crouch/swim/jump/dodge/attack/reload/death, remote interpolation.
3. Terrain: all 15 authoritative tile types, continuous biome transitions, shorelines, water, roads, farmland and terrain overlays.
4. Ecology: all tree and harvestable plant variants, grass, resources, all animal species and their distinct animation states, corpses and harvesting.
5. Construction: foundations and all shapes/tiers, walls/doors/fences/ceilings, placement previews, interior visibility, every production/storage/placeable type.
6. World content: all monument parts and landmarks, underwater objects, projectiles, dropped item models and interaction feedback.
7. Atmosphere: shared day/night and weather, rain/snow, wetness, clouds, fire/smoke, combat and status effects.
8. Removal and verification: remove reachable legacy world-rendering imports/preloads, preserve UI icons, prove gameplay parity and complete representative visual/performance captures.

An initial procedural model is a foundation, not final art. Every asset family must be inspected and refined. Unsupported asset variants must remain visible in diagnostics; generic replacement geometry is not a completion gate.
